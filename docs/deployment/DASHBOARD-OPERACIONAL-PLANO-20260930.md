## Decisão de arquitetura

Uma aplicação nova serve quatro hostnames. O hostname gerencial abre apenas CRM, Orgânico e Influs; cada hostname de equipe abre a sua área. O servidor bloqueia a página `/cx` e consultas com `painel=cx`, mantendo fontes e hospedagem CX atuais para o desenvolvedor. Orgânico e Influs ainda usam o endpoint legado multipainel para ler seus próprios dados; a rota do gateway deve autorizar somente `painel=organico` ou `painel=influs` conforme a sessão. Retirar esse endpoint compartilhado antes de desacoplar essas leituras quebraria esses dois painéis. A mesma aplicação hospeda as páginas e uma API de mesma origem.

Contas individuais usam e-mail corporativo e senha definida por convite único com prazo. O superadmin cria/revoga gestores e concede áreas e edição separadamente. Sessões opacas ficam em cookie Secure/HttpOnly/SameSite/host-only; a API exige origem exata, CSRF para métodos mutáveis e checa área/grant em cada chamada. O banco de contas fica em volume exclusivo com uma réplica. Senhas usam scrypt com custo adaptativo; credenciais individuais dos backends, quando provisionadas, ficam cifradas no servidor. A UI nunca recebe o Bearer real. O superadmin não reutiliza a chave `todos` atual, que ainda inclui CX. O login elimina registros de limite expirados e limita globalmente a 120 tentativas a cada 15 minutos antes do cálculo de senha; um atacante pode consumir esse teto e impedir novos logins durante a janela. Antes da entrada em produção, configurar também limitação por IP de cliente **confiável na borda** e testar a disponibilidade, sem confiar no cabeçalho `X-Forwarded-For` fornecido pelo navegador.

Leitura do Easypanel: os quatro aliases de teste novos têm `middlewares: []`, e não há middleware cadastrado. É possível criar um `rateLimit` e vinculá-lo somente aos IDs desses quatro domínios; as duas operações regeneram a configuração do Traefik **compartilhado**, portanto exigem janela/revisão antes de aplicar e teste de um domínio existente sem alteração. Os registros A públicos dos aliases e do painel apontam ao mesmo IP, mas isso não prova sozinho que o Traefik vê o IP de cada cliente. Antes de ativar, confirmar a cadeia de proxies, testar dois clientes com IPs distintos e tentativa de falsificar `X-Forwarded-For`, verificar TLS/roteamento dos quatro aliases e preparar reversão removendo somente o middleware novo.

O gateway fixa nomes de rotas, métodos, ações, campos e a **URL HTTPS completa** de cada destino conhecido. Uma configuração que troca o caminho de um webhook, mesmo no host aprovado, impede o boot. Rotas dinâmicas do CRM exigem manifesto da revisão de fonte conferida; as que ainda não têm destino revisado ficam indisponíveis. A comparação com o contrato ativo no servidor continua obrigatória antes de configurar qualquer bearer real. O gateway reescreve apenas capabilities cujas URLs coincidam exatamente com as permitidas e remove as demais. O navegador não escolhe URL de upstream. A chamada do navegador termina no mesmo hostname; a chamada do servidor à API existente usa a credencial individual daquela pessoa. O backend continua recusando origens estrangeiras de navegador. Chamadas sem `Origin` são normais entre servidores; nenhuma origem antiga será falsificada. Contratos de escrita sem confirmação segura permanecem fechados até receberem validação específica. O GET de identidade atual atualiza telemetria de uso no banco; leitura autenticada não é tecnicamente zero-write, embora não dispare ação comercial. O `/healthz` prova apenas que o processo/volume estão acessíveis, não a prontidão das integrações.

A checagem do esquema **ativo** dos backends continua pendente. O MCP do Easypanel autentica e permite inspecionar serviços, mas não oferece execução SQL nem criação de papéis PostgreSQL; neste Mac não há `psql` ou credencial de banco destinada a auditoria. A rota SQL existente no n8n usa uma chave compartilhada e aceita consulta arbitrária, portanto não serve para esse diagnóstico. O roteiro `docs/deployment/DASHBOARD-OPERACIONAL-SCHEMA-AUDIT-20260930.sql` foi preparado com consultas fixas de catálogo em transação `READ ONLY`; ele não lê linhas de negócio nem corpos de funções e ainda precisa de revisão/sintaxe validada pelo DBA. Antes da integração real, um administrador do banco precisa provisionar por canal privado uma identidade SQL individual, sem privilégios de dados ou propriedade, e verificar permissões herdadas de `PUBLIC`. Nenhuma consulta SQL ou migração de produção foi feita nesta etapa.

O pipeline novo `.github/workflows/dashboard-operational-shadow.yml` apenas testa e gera um pacote fechado na branch exclusiva/PR. Não possui segredo nem permissão de escrita, e não publica nem reinicia serviços. Assim, atualizações do Git passam primeiro por build e revisão em sombra; a promoção ao Easypanel continua manual e associada a SHA até existir canário com dados reais. A UI e a API do ensaio não concedem edição, pois os contratos de escrita ainda estão fechados.
