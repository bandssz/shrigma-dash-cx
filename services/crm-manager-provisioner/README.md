# Restricted CRM read provisioner candidate

This gateway manages only Growth manager credentials with the exact capabilities `read_content`, `list_history`, `submission`, namespace `dcrm-*` and slot `crm-panel-read`. It does not expose an administrator key, individual bearer, password, arbitrary SQL or writer capabilities. The source is dormant on import; startup is explicit and `enabled` defaults to false. This proposal does not activate a database role, issuer, service, domain or portal flag.

The portal's existing client uses the exact HTTPS hostname `comunicacao-crm-manager-provisioner.tazdb8.easypanel.host`, `Authorization: CRM-Provisioner <separate service token>` and four POST routes: `/internal/v1/crm-managers/prepare`, `/commit`, `/revoke`, `/status`. The first route accepts `prepare_read` or `renew_read`; the others accept their matching fixed actions. Wrong Host, Origin/browser requests, preflight, duplicate auth, aliases, trailing slash, query parameters, unknown fields and writer policy are refused before database access. Host validation binds the protocol destination; it is not a network firewall.

Each RPC obtains one actual Pool lease, checks the fixed connection parameters and negotiated transport, then executes a closed metadata SELECT. It requires database `listmonk`, session/current role `crm_manager_provisioner`, PostgreSQL 17, LOGIN with connection limit 2 and no elevated flags/memberships, EXECUTE on the four wrappers, no helper EXECUTE, no schema/database CREATE and no effective direct table/column privileges on the six relevant tables. Only then does it dispatch one fixed `SELECT public.shrigma_crm_manager_<route>_v1($1::jsonb) AS body`, with a canonical JSON parameter. The database functions independently check the active issuer, role and scope; receipts/errors are validated before release to the caller. The gateway does not SELECT the issuer registry.

Local `GET /healthz` is no longer static success. Only a loopback probe can obtain readiness. It uses the same lease/admission limit, starts `BEGIN READ ONLY`, calls the fixed STATUS wrapper with a fresh random operation UUID and fingerprint, requires its exact `found:false` result for the configured issuer/namespace, then requires ROLLBACK acknowledgement. A failed or incomplete check yields 503. It never prepares, commits or revokes a credential. The response contains only revision, readiness/policy booleans and the fixed role; it does not expose IDs, domains, credentials, connection parameters or database errors. This proves the active issuer/login/RPC boundary when actually run; it does not prove the registry's email-domain equality, which requires the separate reviewed administrator readback.

PG host/port/user/database are fixed to `comunicacao_postgres:5432`, `crm_manager_provisioner`, `listmonk`. `CRM_MANAGER_PG_TLS` must explicitly be `true` or `false`. False requires PostgreSQL's `ssl` setting to be off as well as an unencrypted connection; it is not a downgrade fallback. True requires a bounded CA PEM containing CA certificates, `CRM_MANAGER_PG_SERVERNAME=comunicacao_postgres`, `rejectUnauthorized:true`, and an encrypted, authorized stream with that server name. The pinned pg 8.13.1 driver overwrites a DNS servername with its connection host; therefore the certificate must cover the fixed DNS host. No custom certificate bypass, connection string or ambient PG TLS override is accepted. A server offering SSL must use the verified TLS configuration; a certificate/name mismatch fails closed.

Parameters: `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`, `CRM_MANAGER_PG_TLS`, optional TLS CA/servername, `CRM_MANAGER_ISSUER_ID`, `CRM_MANAGER_NAMESPACE_ID`, `CRM_MANAGER_ALLOWED_EMAIL_DOMAINS` (closed JSON array), `CRM_MANAGER_PROVISIONER_TOKEN`, `CRM_MANAGER_REVISION`, optional `CRM_MANAGER_ENABLED=true`, `PORT=8080`. They belong only in the private runtime environment of the new service. Startup removes PG/password/token/CA entries from the inherited process environment after constructing the private configuration. No credentials are in source, build arguments or image layers. The database receives only a hash/descriptor in the four RPCs, never an individual bearer or password. The separate administrative password/issuer activation flow must enforce its stricter logging checks; this gateway does not change global or role logging settings or pretend to prove that database logging is disabled.

Bounds: headers 8 KiB, request body 4 KiB, strict UTF-8/canonical JSON, response 8 KiB, Pool max 1, one active lease and at most two queued handlers, body deadline 1 s, HTTP deadline 4 s, connection deadline 1 s, PostgreSQL statement/transaction budget 3 s, query deadline 3.5 s. These are configured budgets, not hard wall clock guarantees. HTTP timeout/disconnect retains admission until the lease's work settles; queued or expired work cannot dispatch a late RPC. Client error events are observed without raw output and invalidate the lease. Failed/uncertain leases are destroyed. No automatic HTTP/SQL retry occurs, including loss of an acknowledgement. Existing journal STATUS reconciliation remains the caller's responsibility.

Build context remains the service directory with exactly `Dockerfile`, `package.json`, `package-lock.json`, `server.cjs`; tests/docs/Compose and environment files are excluded. Node22 base and pg 8.13.1 lockfile remain unchanged. Publish through the exclusive candidate image workflow and record its immutable digest and source revision before using the new plan; a successful local build is not a published digest.

The companion Compose builder is a separate preparation artifact. It requires an immutable image digest and source revision; its returned environment is empty. One new service in `dashboard-image-20260930` uses UID/GID1000, read-only root, cap drop ALL, no-new-privileges, .25 CPU, 128 MiB memory and swap, 32 PIDs, heap64 MiB, one replica and no restart. It publishes no container port or PostgreSQL port. Only the new HTTPS domain maps to application port8080. Both Easypanel aliases are bounded to 63 characters. The external Easypanel bridge is necessary to reach the fixed database host; a shared bridge is not a proof of full isolation. The existing BFF requires HTTPS, so private HTTP would need a separate reviewed client contract rather than an implicit URL override. Existing services/routes/domains are outside this proposal.

Before enabling: independently verify role authentication and core ACLs, exact issuer/domain registry, accepted shared-network/PUBLIC ACL boundary and (where applicable) PG TLS; bind only the new role credential and separate service token privately; verify the immutable image, resource limits, local health, exact HTTPS RPC path, namespace and portal flags. Preserved PUBLIC legacy EXECUTE/TEMP permissions mean a stolen database credential is not proven to have only four SQL powers; this HTTP surface is restricted to four RPCs. Keep publication and real activation separate and preserve the administrator/master flow.

Tests run on Node22 without sockets or production access: 31 author tests include three disposable PGlite proofs and injected HTTP/Pool/transport fixtures. They cover the real client→gateway→fixed SQL contract, lost ACK/status recovery, exact admission SELECT grammar, invalid context/role/TLS/ACL, nonstatic health/fresh readonly STATUS, retained lease on deadline, queue/disconnect/stop, limits and secret canaries. PGlite compiles the exact metadata SELECT and refuses its own fixture identity; it does not prove a native PostgreSQL17 login/TLS session or a deployed ingress. Three additional pure Compose/health tests validate the closed plan, immutable image, resource/alias bounds and complete bounded health evidence. No actual broker deployment or role activation has been performed by these tests.
