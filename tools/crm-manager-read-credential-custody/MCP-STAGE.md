# READ stage transport preparation v2 — source only, default OFF

This proposal supplies public plans, a durable effect fence, encrypted-custody wrapper, the exact discovered Easypanel procedure requests, and a callback adapter. Importing the modules does not read keys or environments, open sockets, load PG, call tools, or deploy. `enabled:false` needs no dependencies. `stageApproved` and `readonlyReconcileApproved` are separate approvals; neither is set here. The nine reviewed remote executable files, their pins, the existing custody implementation and the frozen image are unchanged. This is not an activated stage, a new database login, a functional remote acceptance result, or a production release.

## Supported remote sequence

The stage builder derives a separate 128-bit volume namespace from a fixed domain tag plus those two UUIDs; there is no new caller input for that namespace. Rebuilding the same plan preserves its names. Plan SHA binds its new hostname, domain ID, target service, image, source/ledger volume names and Compose bytes. Custody seals an exclusive RSA4096/OAEP-SHA256 + AES-GCM capsule, fsyncs and reopens it before admission and every RPC. Its password and matching SCRAM remain bound to that same intention; no new password, role or intention is created on restart.
2. Admit actual capacity, image/source pins, absent new target, and absent new DNS-equivalent hostname AND domain ID. Admission V1 still requires actual `newVolumesAbsent:true` for stage; V1 false remains a hold. Stage-only V2 instead requires `newVolumesAbsent:false`, `volumeExistence:"unobserved"` and `freshVolumeNamespaceVerified:true`, after verifying both exact names derive from the original IDs. V2 is a reviewed fresh-name policy, not proof that global volumes were enumerated. It is rejected for reconciliation; that path still requires V1 verification of the exact existing source, existing ledger and prior quiescence. Always attempt owned cleanup after a creation attempt: stop ONLY the new target, clear its environment, delete ONLY the bound new mapping after exact ownership checks, and read back disabled + env empty + zero RUNNING + own mapping absent. ## Fresh-volume policy and residual preservation risk

The MCP procedures discovered for this task do not establish global named-volume absence. V2 does not invent that observation. The 128-bit namespace comes from the original randomly generated UUIDs, independently of the 48-bit service suffix. All capacity/resource, target/domain absence, pinned image/source, custody, durable effect fences and both public postcondition barriers remain required.

The initializer refuses occupied, partially initialized, aliased, incorrectly owned or incorrectly permissioned mounts before source writes. It cannot distinguish a genuinely new empty root0755 volume from a foreign existing empty root0755 volume with the same name. A collision could therefore populate that empty volume and change its permissions/owner; exclusive opens prevent source overwrites but are not a global ownership proof. That residual risk is negligible only when the original IDs are freshly generated, preserved and never reused for another execute plan. No forensic global volume inventory or absence guarantee is claimed.

The operator must keep the one exclusive custody directory and original IDs for the entire intention. The existing capsule/fence boundaries refuse the normal second attempt of that same plan; they are not a global registry proving that arbitrary IDs were never reused in another directory or plan. After an unknown outcome, preserve the original ledger and use only the separately approved V1 read-only reconciliation path. Do not change IDs/names to resend stage, reinterpret a persisted legacy48 plan as fresh128, or initialize a replacement ledger. This source proposal adds no timer, scheduler, SQL, new action approval, private credential channel or real-server execution.

## Concrete tool wiring — PREPARED, NOT EXECUTED

In this task, actual MCP functions exist only as `tools.mcp__easypanel__execute_query`, `execute_mutation` and `execute_destructive` inside `functions.exec`. Local Node has crypto/fs/custody and durable fences but no `tools` object or connected MCP client. The functions isolate has no `require`, crypto, Buffer, TextEncoder, process or file API. Therefore passing an `execute` callback in a Node harness is not proof that Node is connected to MCP. `observeStatus` is likewise a private tool-boundary callback, not an implemented direct browser/HTTP client.

A reviewed bridge must keep its output inside a single `functions.exec` orchestration: invoke the approved local Node custody/fence helper with only public arguments and protected input, capture the nested `tools.exec_command` result internally, validate its bounded private DTO against the pinned plan, then call ONLY the literal allowed MCP executor. Never `text`, `notify`, `console`, emit, or return the captured output/private DTO, raw MCP results or errors. It may retain private data solely in approved task-local RAM storage. This is internal captured subprocess stdout, not a claim of zero stdout, zero tool audit or RAM-only remote environment. The custody cipher remains durable on disk; plaintext is never written to a file, Git, image or public response. A secure protected-input implementation, its operational plan-binding checks, runtime resource/capacity observation and the real GET connector are follow-up wiring and are not executed or declared ready here. No real RSA key, capsule, password or PG credential was opened for these tests.

The public callback frame deliberately hides `input`/`env` as non-enumerable. `JSON.stringify(frame.input)` alone omits the secret and MUST NOT be passed to MCP. `mcpArguments(frame)` admits only a locally branded callback frame and explicitly constructs the final private `{procedure,input:{projectName,serviceName,createDotEnv,env}}` with enumerable `env`. That PRIVATE DTO is suitable for connector serialization; it must never be logged or projected. A functions-side bridge must construct the same complete literal in RAM after its private admission, since WeakSet branding cannot cross serialization. Tests assert connector JSON contains the complete synthetic environment while ordinary public projection/inspection contains none of it.
