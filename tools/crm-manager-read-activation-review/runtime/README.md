## Contrato executável

`createRuntime({connect,journal})` devolve `{execute(intent,{verifier}),reconcile(intent,{verifier})}`. Importar não lê env nem cria client/timer/socket. Intent exato: `{schema:'crm-manager-read-runtime-intent-v1',operationId:UUIDv4,credentialIntentId:UUIDv4,action:'stage|activate|disable',fromPhase:'empty|staged|active'}`. IDs são públicos e fixados antes da execução; a credencial correspondente permanece somente na RAM do operador. O UUID de credencial não é prova criptográfica do segredo: igualdade privada do verifier é obrigatória no readback para confirmar staged/active.

`execute` cria intent exclusivo mode0600 e fsync arquivo+diretório antes de qualquer PG I/O. A pasta pai também é fsync após mkdir. Readback inicial READ ONLY admite estado anterior e, em activate, a credencial exata. Uma fence `dispatch` com PID+backend_start é persistida/fsync ANTES do BEGIN mutante. Depois: plano fechado, LOG_SETTINGS+LOG_GUARD/policy, somente então bind SCRAM, mutação exata uma vez, COMMIT uma vez. Nenhum fsync ocorre dentro do orçamento500ms. Erro após fence é `outcome_unknown`, mesmo se a mutação não chegou ao servidor.

O ACK COMMIT é um evento separado fsync. Se persistir ACK falha, não se declara ACK durável. Após ACK, um client novo faz somente READ ONLY; confirmada exige core/roles/issuer e, para staged/active, `pg_authid.rolpassword = current_setting(...)` retornando booleano apenas. Comparação usa o mesmo SCRAM em RAM, sob suppressão de logs antes do bind. O helper de activate também verifica essa igualdade na transação antes de ativar o issuer. O verifier jamais entra no ledger, resultado, query text ou relatório. Strings de segredo não têm garantia de zeroização física; a variável/env local é descartada após o uso.

`reconcile` carrega a MESMA intenção e abre somente transação READ ONLY, sem chamar mutação/COMMIT. Sessão original viva, lock indisponível, estado divergente, verifier diferente/perdido, arquivo corrompido/parcial ou readback falho deixam hold `outcome_unknown`. Estado anterior comprovado é `before_verified` após fence, ou `not_dispatched` sem fence. Nenhum desses estados autoriza replay automático; a mesma intenção nunca volta a executar. Uma nova tentativa exige revisão humana de readback e novo operationId. Não há loop, retry, worker ou renovação automática.

Resultado público fechado: schema/action/state/phase/coreVerified/credentialBound/commitAck. Contém apenas estados/booleanos, sem IDs, segredo, erro nativo, SQL, rows, ACL ou hash de senha. Antes de consumir ACK visível na reconciliação, readDurable valida/sincroniza TODOS os arquivos do prefixo e ambos diretórios, então valida de novo. Falha nesse fsync mantém outcome_unknown; apenas um ACK com essa barreira concluída pode ser declarado durável. Ledger público contém os IDs do plano, pins, PID/tempo do backend e eventos. Arquivos são exclusivos/NOFOLLOW, regulares/nlink1/UID1000/mode0600/até4096bytes; pasta canônica mode0700. Há máximo12arquivos por intenção; uma intenção truncada não é apagada automaticamente para repetir. O driver não encaminha errors/notices/bodies; CLI imprime erro genérico ou envelope.
